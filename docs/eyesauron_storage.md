# EyeSauron — пакованное дедуп-хранилище: спека архитектуры

> Статус: **РЕАЛИЗОВАНА** (2026-08-26). Движок: `services/eyesauron/_pack_store.py`;
> телеметрия: `_telemetry.py`; интеграция в сервис — за флагом
> `config.yaml → eyesauron.store.enabled` (по умолчанию выключен, ingest
> продолжает писать raw PNG). RPC `seal_now`, блок хранилища в `status()`
> и вкладке панели. Контекст: `docs/eyeSauron.md`, сервис `services/eyesauron/`.

---

## 0. Принятые решения

| # | Решение |
|---|---------|
| D1 | Владелец store root — ровно один узел-коллектор |
| D2 | Локальный кэш запечатанных томов после заливки: **100 ГБ** (`local_cache_gb`), вытеснение LRU по возрасту тома |
| D3 | Retention — **заглушка TODO** (в будущем: удаление целых томов + сегментов карт, без компакции) |
| D4 | Размер тома в глобальном конфиге: `eyesauron.store.volume_size_gb: 10` |
| D5 | Целостность: только sha256-верификация при заливке; scrub по расписанию — нет |
| D6 | Bloom-фильтры: поле/файл заложены в формат сразу, включаются по необходимости |
| D7 | **chunker v1 = grid256** (тайлы 256×256, sha256(padded RGB), payload = PNG тайла) — по результатам бенчмарка |
| D8 | Телеметрия доли скролл-кадров в проде → через месяц эксплуатации решение о chunker v2 (CDC-тома) |
| D9 | Формат тома несёт поле `chunker_id` — стратегии сосуществуют в одном хранилище |

Результаты бенчмарка, обосновавшие D7/D8 (см. скрипт для воспроизведения):
спокойный поток — grid256 лучший по хранению/индексу/CPU на обоих профилях;
скролл — grid256 катастрофичен (−26…−41%), CDC стабильно ~80%; cdc_png
(CDC поверх PNG-потока) опровергнута каскадом deflate — не использовать.

## 1. Топология

```
[агенты] ──mesh──► [коллектор: единственный владелец store root]
                        │  локальный диск (NVMe/HDD)
                        ├── store/
                        │    ├── staging.pack / .journal   # активный том (append-only)
                        │    ├── vol-<node>-<seq>.pack     # запечатанные тома
                        │    ├── vol-<node>-<seq>.idx      #   + индексы
                        │    ├── vol-<node>-<seq>.bloom    #   + фильтры
                        │    ├── maps/seg-YYYY-MM-DD.mseg  # дневные сегменты карт
                        │    └── volumes.json              # манифест (авторитетный)
                        │
                        └── NAS (SMB): зеркала готовых томов + манифеста
                             └── store/…та же структура, только sealed+ready
```

Принцип: инжест никогда не ждёт NAS; на NAS — только крупные
последовательные записи иммутабельных файлов.

## 2. Формат тома

### 2.1 `.pack` — данные

Заголовок файла (один раз, 64 Б):
```
0   8   magic 'EYEPACK\0'
8   4   version = 1 (u32 LE)
12  4   chunker_id (u32): 1 = grid256-cs256-png
16  32  резерв (нули)
```

Записи данных, подряд без выравнивания:
```
0   4   'CHNK'                       # маркер для восстановления после сбоя
4   2   flags: бит 0–1 компрессия payload (0 = png, 1 = zstd), остальное резерв
6   2   резерв
8   4   payload_len (u32 LE)
12  32  sha256(payload)              # бинарный, инлайн-верификация при чтении
44  N   payload                      # grid256: PNG-блоб тайла 256×256
```

Футер (последняя запись, тип 'SEAL' вместо 'CHNK'):
```
count записей (u64), created_ts (f64 epoch), crc32 заголовка+оглавления,
sha256 всего файла до футера (вычисляется стримингом при seal)
```

### 2.2 `.idx` — индекс тома (иммутабельный)

Сортированный массив записей по хешу:
```
entry = 32B hash (бинарный) + u64 offset_in_pack + u32 payload_len   # 44 Б
footer: count (u64) + crc32
```
Чтение: mmap + бинарный поиск. Оценки: grid256 ≈ 5.7 тыс. уникальных чанков
на 58 МБ данных → ~4 МБ/ГБ; CDC-чанки дадут в 3–8 раз больше.

### 2.3 `.bloom` — фильтр тома (D6: файл есть, использование опционально)

```
0  8  magic 'EYEBLOOM\0'; 8 8 n_items; 16 8 m_bits; 24 4 k_funcs; …bitmap…
```
Параметры по умолчанию: FPR 1% → m ≈ 9.6·n бит (~300 КБ на 250 тыс.), k = 7,
двойной хеш Кирша–Митценмахера из одного sha256 (`h_i = h1 + i·h2`).
Свойства: ложных отрицательных нет → «нет в bloom» = безопасный пропуск тома;
ложные срабатывания безвредны (проверка по .idx).

### 2.4 Именование

`vol-<node>-<seq>.pack` (например `vol-SysadminPC-000042.pack`) — префикс узла
защищает от коллизий при будущих миграциях; seq монотонный из манифеста.

## 3. Карты кадров

Карта кадра (grid256, совместимо с форматом `_vendor_chunk_store.py`):
```json
{"name": "host/date/ts__title", "w": 1920, "h": 1080, "cs": 256,
 "chunker": 1, "grid": [["hex64", …], …]}          # grid[y][x], row-major
```

Хранение — **дневные сегменты** `maps/seg-YYYY-MM-DD.mseg` (append-only):
```
[u32 len][json карты] × N … [хвостовой индекс: {name → offset}, crc32]
```
Браузинг «host/date» = чтение одного сегмента дня (единицы МБ).
Retention карт (когда появится) — удаление сегмента целиком.

Дедуп-путь инжеста кадра: декод → нарезка тайлов с нулевым паддингом →
hash = sha256(tile.tobytes()) → проверка hot-set/bloom → новые тайлы
аппендом в staging.pack → запись карты в сегмент дня.
Известные тайлы — только ссылка в grid.

## 4. Манифест `volumes.json`

Единственный источник «какие тома существуют». Размер привязан к числу
ТОМОВ, а не чанков: ~150 Б/том → 13 тыс. томов за год ≈ 2 МБ.
```json
[{"id": "vol-SysadminPC-42", "node": "SysadminPC", "seq": 42,
  "state": "ready",            // sealing|sealed-local|uploading|ready|evicted-local
  "size": 10737418240, "sha256": "hex…", "chunks": 250000,
  "created": 1789000000.0, "chunker": 1}]
```
Атомарная запись (tmp + os.replace); один писатель (D1); зеркало на NAS после
каждой смены состояния; восстановление при повреждении — скан каталога +
чтение футеров томов.

## 5. Жизненный цикл тома

```
staging ──seal──► sealing ──► sealed-local ──upload ok──► ready(NAS [+локально])
                                 │                           │
                              crash:                  LRU >100 ГБ (D2)
                         orphan-чистка                       ▼
                                                      evicted-local (только NAS)
```

**Seal** (триггеры: size ≥ volume_size_gb ИЛИ age > max_age_hours ИЛИ RPC):
1) стоп-приём записей (lock, мс) → 2) flush + fsync → 3) футер 'SEAL'
(count, created, crc, streaming-sha256) → 4) сборка .idx (сортировка hot-
индекса) + .bloom → fsync → 5) rename trio (idx/bloom раньше pack) →
6) манифест += запись (sealed-local) → 7) открыть НОВЫЙ staging — аппенды
возобновляются немедленно.

**Upload** (фоновая задача, старейший sealed-local первым):
копия потоком в `<nas>/vol-X.pack.part` со смещения = размер существующего
.part (докачка), sha256 на лету → сверка → copy .idx/.bloom → атомарный
rename в финальное имя → манифест state=ready (+зеркало манифеста на NAS).
Локальная копия остаётся в кэше до вытеснения LRU за бюджет local_cache_gb.

**Восстановление после сбоя**: `staging.journal` — коммит-офсеты (fsync
после данных); при открытии хвост за последним коммитом трекается.
Осиротевшие .idx/.bloom без .pack — удаляются; .pack без записи в манифесте —
кандидат на усыновление (проверка sha256 по футеру).

## 6. Чтение (сборка кадра)

Карта из сегмента дня → для каждой ячейки grid:
hot-индекс (staging + последние K томов) → bloom'ы томов newest-first →
mmap(.idx) бинпоиск → чтение [offset,len] (локальный кэш или NAS range-read)
→ lru_cache байтов чанка (как в vendor) → вставка тайла на канвас,
обрезка паддинга по w/h → PNG наружу.
Смежность новых тайлов одного кадра в staging гарантирует последовательное
чтение недавних кадров.

## 7. Телеметрия скролла (D8)

Цель — измерить ДОЛЮ скролл-кадров на реальном трафике до решения о v2.

При инжесте кадра от агента (коллектор, numpy, ~мс):
- сдвиговая автокорреляция downsampled-градиента текущего кадра с предыдущим
  кадром того же хоста по вертикальным сдвигам −120…+120 px (шаг 4 px);
- если max_corr > порога при сдвиге ≠ 0 → кадр помечается scroll-shift=Δ;
- агрегаты пишутся в локальный jsonl/статистику сервиса: счётчики
  frames_total / scroll_frames по хостам за сутки.

Порог принятия решения о CDC-томах: если scroll_frames/frames_total > ~15%
на значимой части хостов (и объём их потока существен) → включать v2.
Метрика дешёвая и полезная сама по себе (видно профиль активности машин).

## 8. Задел под CDC-тома (v2)

Благодаря D9 внедрение v2 не ломает v1:
- новый `chunker_id = 2 (cdc-raw-zstd)` пишет тома параллельно;
- карта кадра v2: вместо grid — упорядоченный список хешей + w/h
  (сборка = конкатенацияpayload → сырой RGB → PNG);
- читатель обязан поддерживать оба chunker_id (поле в карте и футере тома);
- миграции старых данных нет — тома остаются как записаны.

Из бенчмарка для v2 (когда дойдёт): резать сырой RGB, НЕ PNG-поток;
компрессор zstd (не zlib); помнить о деградации ресинхронизации Gear-CDC
на длинных низкоэнтропийных участках; горячий путь — нативный (Cython/C),
pure-Python ~0.5 с/кадр недостаточен для флота.
