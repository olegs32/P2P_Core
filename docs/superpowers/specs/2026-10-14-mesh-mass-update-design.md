# Массовое обновление mesh-сети — дизайн

Дата: 2026-10-14. Статус: на ревью. Код не писать до аппрува спеки.

## 1. Контекст и бриф

Одним действием с админ-ноды перевести весь мульти-хоп mesh на новый релиз,
собранный `updater.build` (`dist/<ver>/` + `manifest.json` в шаре `releases`).
Оркестратор — новый код только в ядерном `Updater` на админе (фоновая задача
в event loop узла, переживает рестарты панели). Локальная механика
`updater.apply/download` (hash + WinVerifyTrust + `_update.exe` + boot-confirm
+ автороллбэк) не меняется. Политика ошибок — best-effort: идем по всем нодам,
в конце сводный отчет ok/fail/rollback, повторный прогон только по failed.

Ключевая проблема: ребут промежуточного узла рвет транзитный `files`-стрим
дальним. Решение: сначала раскатить exe на все ноды (без ребутоа), затем
веером вызывать `apply` — транзит в фазе apply уже не нужен.

Факт из кода, определяющий дизайн зеркала: `files.serve` отдает только из шар
(`_resolve_ref` → shares), а `updater.download` кладет staged-файл в
`files.download_dir` (`<ver>_Node_P2P_Core.exe`). Поэтому зеркалом становится
постоянная шара поверх `download_dir` — без нового транспортного кода.

## 2. Цели / не-цели

Цели:
- `rollout_start(version)` с админа → сид всего mesh → веер `apply` → отчет.
- Порядок, исключающий самоотрезание: сид ближние→дальние, apply дальние→ближние.
- Повторный прогон только по failed; уже updated/seeded пропускаются.
- Админ по умолчанию не обновляется (`include_self=false` — он уже новый из компиляции).

Не-цели:
- Не менять `apply/download/_confirm_boot_later/_do_rollback`, `MAX_ATTEMPTS`.
- Не вводить новый стриминг; только существующий push-стрим `files`.
- Без селектора режимов ожидания в этом спринте (строго одна схема, см. §6).
- Без децентрализованного gossip-pull (отвергнут в пользу оркестратора).

## 3. Архитектура

Новый код — только `src/internal_modules/updater.py` (+ модели конфига §8,
+ UI-кнопки поверх, отдельным пунктом). Три новых RPC на админе:

- `rollout_start({version, share='releases', include_self=false})` →
  проверка локального `build`-артефакта, построение плана (волны по hop),
  запуск фоновой `asyncio.Task`, немедленный возврат `{ok, plan_id}`
  (волны видны через `rollout_status`). Параметр `share` принимается, но
  фактически игнорируется: шара выводится из первой записи собственных
  `update.sources` админа.
  Долгая работа не блокирует RPC.
- `rollout_status({})` → журнал по нодам `{node, hop, phase, detail,
  version_before/after}`. Фазы: `pending/seeding/seeded/seed_failed/
  applying/updated/rolled_back/apply_failed/unreachable`.
- `rollout_cancel({})` → отмена между фазами/волнами; уже вызванный `apply`
  не прерывается (узел уже в `_update.exe`).

Состояние: в памяти + журнал на диск (`work_dir/rollout_<ver>.json`) для
отчета и повторных прогонов. Пережить ребут самого админа не требуется в MVP
(`include_self=false`), но журнал пишется всегда.

## 4. Фаза 0 — разведка (read-only)

- `netinfo.topology(ttl=4)` с админа → hop-дистанция `hop[node]` (BFS по ребрам
  снимка; для RPC-достижимости важна mesh-маршрутизация `Router`, а не только
  outbound-ребра).
- Параллельный веер `updater.status` + `config.get` по всем нодам (`gather`,
  таймаут ~10с). Ошибки → `unreachable`, план не валят.
- Выход: `waves_seed[0..max_hop]` (ближние→дальние), `waves_apply` — обратный
  порядок; `known-only` без ребер — список `deferred` (пробуем напрямую,
  иначе пропуск с пометкой).

## 5. Фаза 1 — ensure_sources и ensure_cdn (A-примитивы, без рестарта)

Для каждой достижимой ноды через существующие `config.get`/`config.save`:
- источники: в `update.sources` должен быть `{node: <admin>, share}` (имена
  канонизируются к lower). Нет — append в YAML-текст, `config.save({text,
  base_mtime})`. Чужие источники не трогаем. Конфликт по `mtime` — одна
  повторная попытка (перечитать→дописать), затем `failed(conflict)`.
- зеркало: в `files.shares` должна быть `{name: cdn_update, path:
  <download_dir>, allow: []}`, где `<download_dir>` — резолв
  `files.download_dir` (относительный — от `work_dir`). Нет — append аналогично.
- Рестарт не нужен в обоих случаях: `update` входит в `HOT_SECTIONS`, а
  `_sync_live` подменяет секции in-place; `Updater.check` и `Files._cfg`
  (через `config_manager.cfg`) читают новые значения живьем. `restart=false`.

## 6. Фаза A — каскадный сид (ближние→дальние, без ребутоа)

Волны по `hop` от админа, внутри волны батчи 3–5 параллельных. Эталон sha —
`exe_sha256` из манифеста релиза, который оркестратор один раз читает сам
(локальный `dist/<ver>/manifest.json` на админе, проверенный на `start`).
- wave0: оркестратор вызывает на каждой ноде штатный `updater.download`
  (через mesh-RPC `call(dst=N, service='updater', ...)`): нода сама находит
  версию у админа (источники выровнены в §5) и тянет из `releases`-шары.
  Верификация sha — внутри `updater.download` (poll staged + сверка).
- waveN (N≥1): оркестратор вызывает на каждой ноде напрямую `files.download`
  (mesh-RPC на `service='files'` ноды N) с явным источником-зеркалом:
  `{dst: <mirror>, share: cdn_update, path: <ver>_exe, save_as: <ver>_exe}`.
  `updater.download` здесь не годится — он тянет с узла из `update.sources`
  (админ), а не с зеркала. После завершения загрузки оркестратор сверяет sha
  staged-файла ноды с эталоном из манифеста (через `files.stat` ноды:
  `manifest.id` обязан совпасть с `exe_sha256`; mismatch → `seed_failed`,
  файл подлежит перезакачке/удалению).
  После успеха staged-файл ноды автоматически видим следующей волне через ее
  `cdn_update`.
- Fallback без изменений: зеркало умерло/таймаут → ретрай с другого зеркала
  той же волны → деградация в A (напрямую с админа). Resume бесплатно:
  `.part` + offset в `files.download`.
- Волна закрывается best-effort: `seeded` + `failed` со списком причин.
  Ребутоа в этой фазе нет — транзит цел по построению.

Компромисс принят: через `cdn_update` светится весь `download_dir`. Mesh
считается доверенной (по доке `files`), `apply` все равно проверяет
sha256+подпись. Follow-up (не этот спринт): отдельная папка `cdn/` +
`publish`-RPC для изоляции.

## 7. Фаза B — веер apply (дальние→ближние, одно ожидание)

- Канарейка: `apply` на 1 ближней seeded-ноде, дождаться ее `boot_ok`. Ловит
  битый релиз/подпись до массового ребута. Провал канарейки — стоп всего
  rollout с отчетом.
- Затем веер `apply({version})` по всем остальным seeded-нодам, порядок
  дальние→ближние, без ожидания между нодами (батчами).
- Одно общее ожидание `health_confirm_sec`, затем сбор `updater.status`:
  `boot_ok` → `updated`, признаки отката → `rolled_back`, молчание →
  ретраи по §8.
- Статус-опрос не требует транзита через уже ребутнувшиеся — mesh
  реконвергирует, поллер переживает это ретраями.

## 8. Подтверждение и новый конфиг

Локальный механизм не трогаем (`_confirm_boot_later`, `MAX_ATTEMPTS=2`).
Новое поле конфига:

- `update.health_confirm_retries` (int, дефолт 3, интервал опроса ~30с) —
  число попыток опроса `updater.status` оркестратором после первого
  `health_confirm_sec`. Нужно, т.к. массового ребута mesh сходится не сразу.
  Применяется без рестарта (секция `update` горячая).

## 9. Ошибки и отчет

Best-effort везде: `unreachable / seed_failed / apply_failed / rolled_back` —
в журнал, идем дальше. Повторный `rollout_start` с тем же `version`
пропускает `updated/seeded` (staged на месте: `final.is_file + sha` → instant
done) и работает только по failed-множеству. Отмена — только между
фазами/волнами. Финальный отчет — из `rollout_status` + дискового журнала.

## 10. Тестирование

- Юнит: BFS-дистанция из `topology`-снимка; append источника и `cdn_update` в
  YAML без порчи секрета (маска `__MASKED_SECRET__`); пропуск `updated/seeded`
  при повторе.
- Интеграция на тройке admin—B—C: убить B после сида — C доходит через другое
  зеркало/админа; ребут B во время фазы B не валит C (файл уже staged).
- Канарейка с битым manifest/sha останавливает веер до массовой рассылки.
- Ручной прогон: `rollout_status` показывает волны и итоговый отчет.

## 11. Roadmap (не этот спринт)

- `serve_staged`-RPC / отдельная папка `cdn/` для изоляции раздаваемого.
- Селектор режимов ожидания («ждать поволново» vs «файрить и собирать»).
- `include_self=true` (админ обновляется последним, журнал переживает ребут).
- Параллельный опрос fallback-источников релиза (не только админ).
